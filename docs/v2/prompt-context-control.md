# From a request to accountable work

The owner asked for prompt preparation before execution, a clear central-control
hierarchy and one map connecting context, orchestration, autonomy and learning.
For material requests, prepare a short usable brief; do not pursue a perfect
prompt or turn a simple answer into a compulsory workflow.

## What each term means

| Part | Responsibility |
|---|---|
| Prompt preparation | Preserve the original intent; state outcome, scope, constraints, success check, known context, assumptions/gaps and next action. |
| Research and analysis | Acquire missing evidence, judge its quality and reason about the problem; these can refine the brief. |
| Context engineering | Select and budget the current rules, task state, sources, tools and evidence for each actor; preserve scope, freshness and recovery throughout the task. |
| Harness | Provide the execution boundaries, task graph, tool adapters, permission interaction, recovery, checks and persisted state. |
| Orchestrator | Own the canonical brief and goal; choose actions, route optional workers, integrate results and verify completion. It is a role, not another all-knowing model. |
| Loop | A control mechanism inside the harness: use results to retry, diagnose, research or replan within scope and bounds. |
| Memory and learning | Retain inspectable evidence and scoped knowledge. Observations/corrections can become candidates; independent evaluation precedes promotion. This is not online model training. |

## Central control hierarchy

1. **Authority:** owner intent and native/platform policy. A brief or retrieved
   document never expands authority, changes valid acceptance or bypasses refusal.
2. **Accountable orchestration:** canonical goal/brief, scoped context selection,
   method/model-effort routing, ownership/scheduling, checks and recovery.
3. **Execution:** direct work or optional workers with bounded tasks, disjoint
   write scopes and appropriate tools. Parent integration remains necessary.
4. **Local evidence plane:** original sources, task graph, handoffs, outputs,
   receipts, scoped facts and candidate learning. Actors inspect this plane rather
   than running chat-to-chat heartbeats.

The four conceptual layers remain framework/workflow, methodology,
philosophy/first principles and knowledge vault. The central control hierarchy
describes their responsibilities, not a newly deployed permanent daemon or a
universal controller that reroutes every application's chats.

## Implementation and evidence boundary

- The source launch packet includes preparation guidance by default for both
  existing and adaptive method policies. It preserves task bytes and source
  bindings, performs no task effects and keeps task evaluation NOT_RUN.
- Shared work-loop guidance describes preparation before writes or delegation,
  relevant retrieval before questions, and direct handling for trivial requests.
- Global/native instructions and package overlays require an explicit reversible
  local activation receipt. A source edit alone is not an installation.
- Native hooks and approval settings remain unchanged. Instructions cannot
  guarantee that every current or dormant session follows the procedure; cold
  fixture checks qualify observed behaviour only.
- Native smoke attempts, usage and limitations belong under the existing local
  prompt-preflight evidence directory; no global efficacy, token-saving or final
  v2 claim follows from them. Automatic validated procedure promotion stays held.

existing: launch.prepare, method_control.decide, work-loop/reasoning/recovery,
project memory and SourceVault, plan/handoffs, standards, native Codex CLI.
No new framework, model, hook, plugin or permission profile is required.
